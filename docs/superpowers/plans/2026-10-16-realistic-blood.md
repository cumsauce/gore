# Realistic blood — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the symmetric-starburst splats with directional, angle-aware impact spatter grounded in forensic bloodstain physics, and add animated blood that drips down vertical surfaces.

**Architecture:** The splat look lives in two places that already exist — the decal atlas (`blood_atlas.png`, sampled as model quads by `StainQuad`/`DecalRenderer`) and the server-side placement in `Bleeding`. Phase 1 regenerates the atlas with directional shapes and teaches placement to orient each splat along its travel direction, pick elongation from impact angle and size from velocity, and bias the ray cone along the impact direction. Phase 2 adds a persistent, age-animated "run + bulb" drip. Phase 3 polishes pools, cast-off and wicking.

**Tech Stack:** Java 25, Fabric Loom 1.18.2, Minecraft 26.3, Fabric API 0.162.0+26.3. Atlas generated by a committed stdlib-Python script (no PIL/ImageMagick on this machine; write PNG bytes with `zlib` + `struct`). No new dependencies, no Mixin, no custom pipeline.

**Spec:** `docs/superpowers/specs/2026-10-16-realistic-blood-design.md`

## Global Constraints

- Target Minecraft `26.3` (unobfuscated), `gradle.properties` unchanged: `minecraft_version=26.3`, `loader_version=0.19.5`, `loom_version=1.18.2`, `fabric_api_version=0.162.0+26.3`. Build with `./gradlew`, JDK 25 (`/opt/homebrew/opt/openjdk@25`).
- **No Mixin, no custom render pipeline.** Rendering stays on the model feature (`SubmitNodeCollector.submitModelPart`) and the existing particle path.
- **Purely cosmetic.** Nothing may damage, slow, or otherwise affect gameplay.
- **Directionality is law.** No splat may be symmetric; every elongated stain's tail points away from the wound along the droplet's travel direction.
- The atlas is a committed artifact produced by a committed script; the script's physics constants are the single source of truth and must be re-runnable.
- Existing behaviour must not regress: wall decals still persist and sync, body stains still weld to the model, particles still tint red, the GUI icon still draws.
- The image-authoring reality of this environment: the model cannot view images, so every "does it look right" check is done with `dominant.py <png> <r> <g> <b> <tol>` (pixel stats + bounding box) and reasoned from the rasterisation math, never by eye.
- All new server/shared classes go in `src/main/java/dev/lume/gore/`; all client classes in `src/client/java/dev/lume/gore/client/`.

## Review Focus

1. **A straight-on hit (90°) must not look elongated.** `sin(angle) ≈ 1` must select the round band; the elongation math must clamp at the round end, not divide toward infinity.
2. **A grazing hit must not divide by zero.** `sin(angle) → 0` must clamp to the shallowest band, never produce NaN/∞ size.
3. **Tails must point away from the wound for every ray.** The rotation must be computed from the *projected travel direction* and must be stable (no flips) across the whole cone, including rays that hit near-parallel to the face.
4. **A hit against a floor or ceiling** (face UP/DOWN) still places a decal and the rotation/elongation must not blow up when the travel direction is nearly normal to the face.
5. **The regenerated atlas must match the cell math** the renderer uses — a mismatch between the script's cell grid and `CELL`/`SHEET`/`cellX`/`cellY` in the Java would silently sample the wrong sprite.

### Task 1: The atlas generator

A committed Python script that draws directional splats from the physics and writes the 256×256 atlas. This is the foundation; every later task samples its output.

**Files:**
- Create: `tools/gen_blood_atlas.py`

**Interfaces:**
- Consumes: nothing.
- Produces: `tools/gen_blood_atlas.py` (run `python3 tools/gen_blood_atlas.py` → writes `src/main/resources/assets/gore/textures/decal/blood_atlas.png`).

- [ ] **Step 1: Write the script, stdlib only (zlib + struct for PNG)**

The atlas is a 256×256 RGBA image, 4×4 grid of 64px cells. Cell `i` is at `(x = (i%4)*64, y = (i/4)*64)`. Every cell is transparent except where a splat is drawn; the splat's tail points **up** (toward `-y` in the image, i.e. the cell's top edge).

Impact cells (0–11) are laid out as 4 elongation rows × 3 satellite-density columns. `cell = elongationBand * 3 + densityBand`:

- elongation bands 0–3 → `sin(angle)` target ≈ `[1.0, 0.7, 0.45, 0.25]`, i.e. round → increasingly shallow. Ellipse semi-major `a` along the tail axis and semi-minor `b` across it satisfy `b/a = band value` (band 0 is a circle).
- density bands 0–2 → satellite count `[0, 4, 9]`, satellite radius decreasing with count.

Draw order per impact cell: (1) a filled ellipse centred slightly below cell centre (so the tail has room above), radius `a` = 24px down the tail axis, `b` = `a × band value`; (2) a darker "spine" line from the ellipse centre to the tail tip (a 3px-wide line along the tail axis); (3) the satellites as small filled circles (1–3px) scattered *past* the tip, biased along the tail axis, none behind the ellipse. Colours: base blood `(120, 14, 14, 255)`; spine and satellites darker `(90, 8, 8, 255)`; a subtle 1px lighter edge on the ellipse's leading side `(150, 24, 20, 255)`.

Pool cells (12–13): a filled rounded blob (an ellipse at band 0) drawn *without* a tail, meant to sit on a floor — two size variants. Drip cells (14–15): a thin vertical "run" strip plus a teardrop bulb at the bottom — a ~6px-wide vertical line ending in a ~16px bulb — two length variants (reserved for Phase 2).

Write a correct PNG with `struct` (signature, IHDR, IDAT with `zlib.compress` over scanlines prefixed by filter byte 0, IEND), 8-bit RGBA, no colour type 6 alpha premultiplication.

- [ ] **Step 2: Run it and verify the PNG is well-formed and the right size**

Run: `python3 tools/gen_blood_atlas.py`
Then: `python3 /private/var/folders/tb/8d_73tkx5hndlyfwjng3srp80000gn/T/opencode/pngtool.py load_png src/main/resources/assets/gore/textures/decal/blood_atlas.png`
Expected: reports `256 256 4` and a byte length of `256*256*4`.

- [ ] **Step 3: Verify the elongation bands actually differ**

For each impact cell, `dominant.py <png> 120 14 14 40` restricted to the cell's 64×64 region (crop first with `pngtool.py crop`), and confirm the red `bbox` is square for band 0 and increasingly tall/narrow for bands 1–3. Record the bbox heights in the report.

```bash

git commit -m "Generate a directional blood atlas from spatter physics"
```

### Task 3: Directional, angle-aware placement

The core realism change. Every splat is oriented along its travel direction, elongated by impact angle, sized by velocity, and the rays form a cone.

**Files:**
- Modify: `src/main/java/dev/lume/gore/Bleeding.java`

**Interfaces:**
- Consumes: the atlas cell layout from Task 1 (`elongationBand * 3 + densityBand`).
- Produces: `decalAt(BlockHitResult hit, Vec3 travelDir, float severity, RandomSource random)` returning a `Decal` whose `rot` is the travel direction's angle on the face and whose `variant` is chosen by angle/velocity.

- [ ] **Step 1: Thread the travel direction through**

`collectDecals` already computes `rayDir` per ray before clipping. Pass `rayDir` into `decalAt` (replacing the unused-in-rotation `variant` argument) so the decal can orient itself.

- [ ] **Step 2: Compute impact angle, elongation band, and rotation**

In `decalAt`, with face normal `n` (from `hit.getDirection()`) and travel direction `d = rayDir` (points into the surface): the impact sine is `s = clamp(|d·n|, 0, 1)`. Map `s` to an elongation band: `band = 0` when `s ≥ 0.85`, `1` when `s ≥ 0.6`, `2` when `s ≥ 0.35`, else `3`. Project the travel onto the face: `p = d - (d·n)n`; if `|p|` is near zero (a straight-on hit) fall back to the face's `axis1`. The decal rotation `rot` is the angle of `p` in the face's tangent basis, measured so that the sprite's tail (up) lands on `p`: `rot = degrees(atan2(p · axis2, p · axis1))`.

- [ ] **Step 3: Pick size and density from velocity**

The ray speed is `|d|` (the ray length encodes nothing today — use a per-ray velocity value the caller already varies, or derive speed from the ray's current `rayDir` length which the spray loop scales by severity). Map speed to a density band (`0` slow → no satellites, `2` fast → many) and scale `size` down as speed rises (faster droplets are smaller). `variant = elongationBand * 3 + densityBand`.

- [ ] **Step 4: Bias the rays into a cone**

In `collectDecals`, the jitter `random.nextGaussian()*0.35` per axis is isotropic. Replace it so the direction is `dir` plus a lateral jitter whose magnitude falls off with angle from `dir`, keeping the spray concentrated along the impact direction rather than a sphere.

- [ ] **Step 5: Verify it compiles and a directional hit renders**

Run: `./gradlew compileJava`, then `./gradlew runClientGameTest`, then `dominant.py ~/gore-run/clientGameTest/screenshots/0002_gore-splatters.png 120 14 14 45`.
Expected: compile clean, red present on the wall, and (comparing to the pre-change run in Task 2's report) the splatter is visibly asymmetric — the red bbox leans away from the player. Record the bbox.

- [ ] **Step 6: Commit**

```bash
git add src/main/java/dev/lume/gore/Bleeding.java
git commit -m "Orient splats along travel and elongate by impact angle"
```

## Self-review

**Spec coverage.** Phase 1 (directional atlas, angle/velocity-aware placement, cone) maps to Tasks 1–4. Phase 2 (drips/flow) and Phase 3 (pools/cast-off/wicking) are explicitly deferred with their rationale, per the spec's own ordering ("Phase 1 ships first"). Every spec non-goal and anti-goal is restated in Global Constraints and Review Focus.

**Step scan.** Each step names a file, an exact constant, or a command with an expected result. The physics constants (band thresholds, ellipse radii, colours, satellite counts) are pinned in Task 1 Step 1 and Task 3 Steps 2–3 so an implementer does not invent them. The two places an implementer might diverge — the cell grid mapping and the rotation formula — are given as exact formulas.

**Type consistency.** `variant = elongationBand * 3 + densityBand` is defined once in Task 1 and consumed identically in Task 3. `CELL`/`SHEET` and `CELL_PIXELS`/`TEXTURE_SIZE` are the only size constants and are changed together in Task 2. `decalAt`'s new `travelDir` parameter is introduced in Task 3's interface block and used there only.

**Review Focus.** Each of the five lines has a home: 90° clamp is Task 3 Step 2 (`s ≥ 0.85` → band 0), grazing division is Task 3 Step 2 (`clamp(..., 0, 1)`), tail stability is Task 3 Step 2 (the `|p| ≈ 0` fallback), floor/ceiling is Task 3 Step 2 (face-agnostic tangent basis), atlas/cell-math agreement is Task 2 Step 1–2 plus Task 1 Step 3's per-cell check.

**Proportion.** The plan specifies the decisions an implementer cannot make alone — the physics constants, the cell layout, the rotation formula, the size map — and leaves the rasterisation loop and the plumbing as the body they write. No function body is reproduced that the signature and pinned constants already determine.
